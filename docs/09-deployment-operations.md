# 部署与运维说明

## 1. 环境划分

- Local：开发者本机，使用容器化 PostgreSQL 和模拟附件存储。
- Test：团队联调与自动测试，不含真实敏感数据。
- Staging：接近生产配置，用于迁移、恢复、安装包和用户验收。
- Production：正式环境，仅经审批的发布流水线可变更。

每个环境使用独立数据库、密钥、对象存储和登录凭据。

## 2. 推荐部署形态

首选小型云服务器或可靠托管环境：反向代理/HTTPS → NestJS API/Worker → PostgreSQL；附件使用兼容对象存储。服务通过 Docker Compose 编排，但生产数据库是否容器化应根据可维护能力决定，优先托管 PostgreSQL。

若只能店内自建：需要 UPS、固定主机、路由器端口安全、异地备份和手机远程访问方案。禁止直接把数据库端口暴露到互联网。

## 3. 配置与密钥

- 仓库只保存配置模板和变量名称。
- 数据库密码、JWT 签名材料、对象存储密钥由部署环境注入。
- 启动时校验必需配置，缺失则明确失败。
- 密钥轮换有记录；旧密钥的兼容窗口与撤销步骤明确。

## 4. 发布流程

1. CI 完成构建、测试、扫描并生成不可变版本产物；
2. 在 Staging 从生产结构副本演练迁移与回滚；
3. 发布前确认备份可用、变更说明和维护窗口；
4. 先运行向后兼容的数据库迁移，再滚动/替换服务端；
5. 运行健康检查和核心业务冒烟；
6. 分发签名的桌面/手机安装包；
7. 观察错误率、延迟、数据库连接和对账结果；
8. 达不到门槛按预案回滚。

## 5. 客户端升级

- API 至少兼容当前和上一个受支持客户端版本。
- 强制升级只用于安全或数据正确性问题，并提前提示。
- 本地 SQLite 迁移必须可从每个受支持版本升级，失败时保护草稿并给出恢复方式。
- Windows 安装包签名；Android 使用受控签名密钥；iOS 按 Apple 发布要求执行。

## 6. 健康检查与监控

- 存活检查：进程可运行；就绪检查：数据库等关键依赖可用。
- 监控 API 请求量、错误率、P95 延迟、数据库连接/慢查询、磁盘、备份状态、Outbox 积压。
- 业务监控：过账失败、余额对账差异、异常负库存、编号冲突、重复幂等请求。
- 告警必须有负责人、级别和处置步骤，避免无人负责的噪音。

## 7. 日志与诊断

- 使用结构化日志，包含环境、版本、追踪 ID、用户 ID（非姓名敏感值）、业务对象 ID。
- 客户端错误上报去除敏感信息，并允许用户复制问题编号。
- 生产日志设保留期与访问权限；不得长期无限增长。
- 每次发布记录版本、提交、迁移、时间、操作者和结果。

## 8. 日常运维节奏

- 每日：检查备份、错误告警、磁盘和异常业务对账。
- 每周：检查慢查询、失败任务、未处理安全更新和用户反馈。
- 每月：恢复演练、权限复核、结账与余额对账、容量趋势。
- 每季度：灾难恢复演练、依赖升级计划、安全和交接文档复核。

## 9. 故障处置底线

数据库异常、重复过账或余额不一致时，先停止高风险写入并保留证据；不得直接在生产表手工改数字。通过可复现查询确认范围，使用经审查的修复迁移/调整单，并在修复后运行全量对账。
