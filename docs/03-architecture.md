# 系统架构说明

## 1. 架构结论

采用 **Tauri 2 + React/TypeScript 统一客户端、NestJS 模块化单体、PostgreSQL 单一事实源**。Windows 与 Android 共享响应式业务 UI，平台外壳只承担安全存储、扫码、文件、更新和打印适配。先用结构清晰的单体保证交易一致性与低运维成本；只有出现可量化的独立扩容或组织边界时才拆分服务。

```text
Windows 桌面端 ─┐
Android/iOS 端 ─┼─ HTTPS/JSON ─ API 服务 ─ PostgreSQL
管理 Web（可选）┘                ├─ 对象存储（图片/附件）
                                ├─ 后台任务（报表/备份通知）
                                └─ 日志、指标、审计
```

## 2. 技术选型

| 层 | 技术 | 选择理由 |
|---|---|---|
| 跨端客户端 | Tauri 2 + React 19 + TypeScript + Vite | 官方覆盖主流桌面和移动平台；Windows/Android 共享 UI，安装包较轻 |
| 服务端状态 | TanStack Query 稳定版 | 统一请求缓存、失效和错误状态；本地表单状态保持局部 |
| UI | Tailwind CSS + 项目自有 shadcn/ui 风格组件 | 响应式、可访问、代码归项目维护；形成统一设计令牌 |
| 本地数据 | SQLite + Tauri SQL 插件 | 受控缓存、草稿和同步队列；不是最终账本 |
| 服务端 | Node.js 24 LTS + NestJS / TypeScript | 与客户端统一语言，模块、验证、授权和 OpenAPI 能力成熟 |
| 数据访问 | Prisma ORM 稳定版 + 必要时参数化 SQL | 类型化访问、迁移与事务；钱使用 Decimal，热点查询经分析后优化 |
| 数据库 | PostgreSQL 18 | 可靠事务、约束、索引、JSON 和成熟备份工具 |
| API | REST + OpenAPI | 易生成客户端、便于联调和交接 |
| 认证 | NestJS 认证/授权机制 + JWT/轮换刷新令牌 | 密码哈希、锁定、设备会话与角色权限由项目完整实现并测试 |
| 部署 | Docker Compose，反向代理提供 HTTPS | 小规模低运维；保留迁移到托管容器/数据库的能力 |
| 测试 | Vitest + Testcontainers + Playwright | 使用真实 PostgreSQL 验证事务与约束，并覆盖完整业务链 |

依赖版本必须在代码落地当天查阅官方支持策略并写入锁文件；上述大版本是架构基线，不是永久升级授权。

## 3. 服务端模块

```text
Identity        用户、角色、权限、登录会话
Catalog         商品、分类、品牌、规格、单位、条码
Parties         客户、供应商、联系人、信用信息
Purchasing      采购、入库、采购退货
Sales           销售、出库、销售退货
Inventory       仓库、库存余额、库存流水、盘点、调拨
Receivables     应收、收款、核销、账龄
Payables        应付、付款、核销、账龄
Cash            资金账户、费用、其他收入、转账
Reporting       看板、对账单、经营报表、导出
Audit           操作审计、业务事件、异常追踪
Administration  参数、编号规则、备份状态、导入任务
```

每个模块拥有自己的应用用例、领域规则和数据访问映射。模块之间通过明确接口或进程内领域事件协作，禁止任意跨模块直接改表。

## 4. 建议代码结构

```text
apps/
  client/                  React/TypeScript 共享 UI
    src-tauri/             最小 Rust 平台外壳
  api/                     NestJS 模块化单体
    src/modules/<module>/
    test/unit/
    test/integration/
packages/
  contracts/               由 OpenAPI 生成的 TypeScript 客户端/类型
  domain/                  无框架的值对象与可共享纯规则
  design_system/           颜色、字体、组件、图标封装
infra/
  compose/                 本地与部署编排
  migrations/              运维脚本（数据库迁移仍由服务端工程管理）
docs/
```

不为了“看起来先进”预建大量空层。一个业务用例的输入、校验、授权、事务、输出和测试应能被快速追踪。Rust 外壳不放业务规则；共享规则只改善体验，正式过账仍由服务端重算。

## 5. 写入链路

```text
客户端命令
  → API 鉴权与权限
  → 输入/业务规则校验
  → 开启数据库事务
  → 幂等检查
  → 更新聚合与余额快照
  → 写不可变业务流水/审计/Outbox
  → 提交事务
  → 返回单据版本与结果
```

关键表使用版本号做乐观并发控制；库存最后一件等竞争场景使用条件更新或合适的行级锁，并由集成测试验证。

## 6. 离线策略

首版采用“在线过账、有限离线”：

- 商品、客户和近期单据可缓存供查询；
- 断网时允许保存明确标识的本地草稿；
- 恢复网络后由用户确认提交，服务端重新检查库存、价格、信用和权限；
- 正式销售、库存、收付款过账必须由服务端确认；
- 不承诺两个离线设备同时修改账本后自动无冲突合并。

如果业务确认必须完全离线开单，应单独立项同步协议、冲突策略、设备信任和审计；不得用简单“最后写入覆盖”处理财务数据。

## 7. API 约定

- 路径按资源与用例设计，版本前缀 `/api/v1`；
- 使用 RFC 9457 Problem Details 表达错误；
- 写请求带 `Idempotency-Key`；并发编辑带版本/ETag；
- 分页、排序、筛选和时间格式统一；
- OpenAPI 是跨端契约，由 CI 校验破坏性变化并生成客户端；
- 日志使用追踪 ID，但绝不记录密码、令牌或完整敏感凭据。

## 8. 数据一致性

- PostgreSQL 是正式账本唯一事实源；SQLite 仅缓存和草稿。
- 同一业务过账需要强一致事务。
- 邮件/消息/报表生成等外部副作用通过事务 Outbox 异步处理。
- 余额快照提高查询速度，不替代流水；需要提供对账作业发现差异。

## 9. 不选方案说明

- 首版不拆微服务：用户量与团队规模不支持其部署、事务和排障成本。
- 不使用纯客户端数据库共享文件：并发、审计、手机访问和备份风险过高。
- 不以 Excel 作为数据库：缺少事务、权限、可靠约束和多端一致性。
- 不以 Flutter 作为首选：可行，但会形成 Dart 客户端与 TypeScript 服务端双语言栈，当前没有足以抵消交接成本的明确收益。
- 不直接依赖 Tauri 完成所有打印：打印先做真实设备 PoC；若无法稳定覆盖目标打印机，保留 React UI 并仅将 Windows 外壳切换 Electron。

## 10. 架构质量门禁

- 新模块必须写明职责、依赖和数据所有权。
- 禁止循环依赖、跨层引用 UI、控制器直写数据库、通用 `Utils` 垃圾箱。
- 数据库约束与业务校验双保险；关键规则必须有集成测试。
- 只有测量到性能问题后才缓存或引入新基础设施，并记录 ADR。
