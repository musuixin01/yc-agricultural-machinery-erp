# AI 项目上下文

## 目的

本文件为参与开发、审查或排障的 AI 提供稳定上下文。根目录 `AGENTS.md` 是执行入口；各专题文档是相应规则的唯一来源。

## 一句话产品定义

“玉春”（简称 YC）为个体农机商户提供 Windows 与手机协同的商品、采购、销售、库存、应收、应付和资金流水管理，所有关键数字可追溯、可核对、可恢复。

## 已定方向

- Tauri 2 + React/TypeScript 统一客户端，Node.js 24 LTS + NestJS 模块化单体，PostgreSQL 18。
- REST/OpenAPI 契约；SQLite 只做缓存和离线草稿。
- 首版在线正式过账，不做多主离线账本合并。
- 普通商品默认移动加权平均成本；正式金额使用十进制定点。
- 已过账单据不可直接编辑/删除，通过冲销或调整纠错。
- 首版是经营 ERP，不冒充法定总账或税务申报系统。

这些是架构基线。当前工具链版本以 `pnpm-lock.yaml`、各应用 `package.json` 和已接受 ADR 为准。

## 业务语言

- 客户欠款：经营界面统一称呼；在账务、接口和数据库语境中称为应收账款。禁止使用“客户欠我们”或“客户应付”。
- 我们欠供应商：应付账款。
- 过账：让草稿成为正式业务，同时产生库存/往来/审计影响。
- 核销：把收付款金额分配到具体应收/应付发生项。
- 冲销：以有来源的反向记录抵消已过账错误，不擦除历史。
- 余额快照：加速查询的受控派生数据，可由流水重建。

## 高风险不变量

修改以下任一行为时，必须先读取 `docs/02-business-processes.md` 和 `docs/04-data-model.md` 并补集成测试：

- 采购/销售/退货/盘点/调拨过账；
- 库存数量或成本；
- 应收、应付、收付款、预收预付、核销；
- 单据状态、作废、冲销、结账；
- 幂等、并发或数据库事务。

验证结果至少能回答：是否重复生效、失败是否完整回滚、余额是否可由流水核对、无权限调用是否被拒绝、并发边界是否安全。

## 模块所有权

- Catalog：商品、分类、品牌、规格、单位、条码。
- Parties：客户、供应商及信用资料。
- Purchasing / Sales：采购销售单据与状态。
- Inventory：仓库、库存账本、盘点、调拨、成本。
- Receivables / Payables：欠款发生、收付款、客户预收款、供应商预付款与核销。
- Cash：资金账户、费用、其他收入、转账。
- Identity / Audit / Reporting / Administration：横向能力。

跨模块通过公开应用接口或领域事件协作；模块只能直接维护自己拥有的数据。

## AI 变更输出

每次交付说明：完成的业务结果、改动文件、数据库/API 兼容影响、执行的验证、尚未验证的现场事项和明确风险。涉及新依赖时说明必要性、官方支持状态和替代方案；涉及架构决策时新增或更新 ADR。

## 当前状态

Inventory 的不可变库存账本已开放正式明细查询：服务端按商品名称、编号、条码和业务类型筛选并分页，返回原始单号、仓库、数量增减、成本、业务日期与过账人。客户端不得自行拼接或伪造库存流水。

Sales 已过账和已冲销单据支持正式销售凭证预览、浏览器打印、PNG 保存及手机系统分享。已冲销凭证必须带水印；Web Share 不支持文件时必须提示先保存图片。用户已明确暂缓仓库调拨。

Administration 已实现正式门店资料单例：只保存经营者确认的名称、简称、电话、地址、票据说明和 A4/80mm 默认尺寸，更新使用乐观版本并写审计。销售凭证必须读取该配置；空电话和地址不得用示例值补齐。

Receivables 已实现正式客户对账单：只按服务端正式应收相关事实重建指定期间的期初、本期增加、本期减少、期末与逐笔结余。赊账销售和收款反核销增加客户欠款；客户收款、预收抵扣、销售退货及赊账销售冲销减少欠款。散客现结不得混入；客户端不得自行用销售额减收款推算。查询最多 366 天，支持 A4 打印、PNG 保存和系统分享，但不是法定会计账簿。

Receivables 已实现客户收款凭证：凭证只能由服务端已入账 CustomerReceipt 生成，不得独立创建收款或在客户端修改金额、客户、账户和核销关系。一张收款可列示多张销售单核销；过账成功自动预览，历史记录允许补打。已反核销收款的凭证必须保留且醒目标为“已反核销，不能作为有效收款证明”，不得继续显示为有效收款。A4/80mm、PNG 与系统分享是同一正式收款事实的不同输出形式。

Payables 已实现供应商付款凭证：凭证只能由服务端已入账 SupplierPayment 生成，不得独立创建付款或在客户端修改金额、供应商、账户和核销关系。一张付款可列示多张采购单核销；过账成功自动预览，历史记录允许补打。已反核销付款的凭证必须保留且醒目标为“已反核销，不能作为有效付款证明”，不得继续显示为有效付款。A4/80mm、PNG 与系统分享是同一正式付款事实的不同输出形式。

Payables 已实现正式供应商对账单：只按服务端正式应付相关事实重建指定期间的期初、本期增加、本期减少、期末与逐笔结余。采购入库欠款和付款反核销增加供应商欠款；供应商付款、采购退货和预付款抵扣减少欠款。付款草稿与待过账付款不得混入，客户端不得拿当前未付余额倒推历史。查询最多 366 天，支持 A4 打印、PNG 保存和系统分享，但不是法定会计账簿。

Reporting 已实现真实经营看板，桌面端和手机端共用 `GET /api/v1/reporting/dashboard`。首页只展示正式账本支撑的销售净额、退货、客户欠款、我们欠供应商、库存预警和资金余额；销售与退货/冲销按业务日抵减，应收应付直接汇总未结余额，资金从 CashBalance 读取。接口失败不得以零值或演示数据代替。用户已明确暂不开发经营费用与其他收入。

Administration 已实现数据备份与恢复中心：只允许 `administration.manage` 创建、复核、下载和恢复本系统生成的 PostgreSQL 自定义归档。每份备份必须同时通过 SHA-256 和 `pg_restore --list` 校验；恢复前必须自动创建当前数据快照，要求输入带备份编号的二次确认，并用单事务恢复。每日自动调度和第二存储副本已实现，但当前只覆盖单 API 实例和业务数据库，不包含附件、集群角色/表空间或 `PII_ENCRYPTION_KEY`。

Cash 已实现资金账户间正式转账：只允许两个不同的启用账户，在 Serializable 事务内按固定顺序锁定账户，转出余额不足时整笔回滚；转出与转入成对写入不可变资金流水且净额为零。转账目前不支持反向单据，录错后的纠正功能必须单独建模，禁止直接改余额或删除流水。

正式代码位于 `apps/client` 与 `apps/api`。产品名称统一为“玉春”，简称“YC”。UI 采用 AC 组合：大于等于 761 CSS 像素使用 A 桌面布局，低于 761 使用 C 移动布局。Catalog 商品资料与 Parties 客户/供应商模块已实现，数据保存在 PostgreSQL，均支持列表、搜索、创建和乐观并发启停；细节见 `docs/modules/catalog.md` 与 `docs/modules/parties.md`。

`apps/ui-prototype` 仅保留早期原型，不应继续在其中开发正式功能。Parties 只拥有主体、角色、联系人和信用资料，绝不能直接保存可编辑的应收/应付余额。Warehouses 只拥有仓库与库位，不保存可编辑库存余额。Identity 已实现经营者初始化、登录、令牌轮换、员工账号、四类预置岗位、启停、密码重置、设备会话撤销、服务端权限与基础审计。Inventory 已实现期初库存、不可变库存账本、整仓库存盘点和独立库存报损。盘点自动冻结正库存商品的数量、成本和余额版本，只接受实盘数量并由服务端计算差异；盘点期间任一余额变化都会让整单过账失败，禁止旧快照覆盖新业务。报损用于明确损坏、锈蚀或淘汰的商品，按过账时移动平均成本扣减库存；任一商品库存不足时整单回滚。Purchasing 已实现采购入库、关联原单采购退货、库存成本扣减、应付减少和已付款部分供应商退款；细节见 `docs/modules/purchasing.md`。Payables 已实现资金账户、供应商付款、指定核销、整单付款反核销、供应商预付款和后续应付抵扣；普通付款仍必须全部分配到已有应付，预付款必须保存独立原始金额与可用余额，不得伪装成负应付，细节见 `docs/modules/payables.md`。Sales 已实现销售出库与退货，Receivables 已实现正式客户欠款查询、门店快速收款、整单收款反核销、客户预收款及后续抵扣；预收款必须独立保存且不得伪装成负应收。采购订单、分批收货、库存调拨、独立客户退款、独立供应商退款、预收预付款退款与部分收付款反核销尚未实现；任何仪表盘旧页面的演示数字均不得当作正式业务事实。

Administration 的备份恢复已使用正式 PostgreSQL `pg_dump` / `pg_restore` 流程，并提供每日自动备份策略。策略独立保存在备份目录的 `policy.json`，不会被业务库恢复覆盖；只自动清理超出保留数量的 `AUTOMATIC` 备份，手动备份与恢复前快照不得被自动删除。自动备份可复制到经营者配置的第二绝对目录，复制完成后必须重新计算 SHA-256，再原子写入归档与元数据；第二存储失败不得否定已经成功的本机备份，二者状态必须分别记录。经营看板向有管理权限的用户显示失败提醒。当前调度只支持单 API 实例；操作系统推送、云服务上传和外部归档导入仍未实现。

Sales Return 已实现直接关联已过账原销售单的部分/整单退货。累计退货数量不得超过原销量，商品按原销售成本回原仓；现结销售实际退款，赊账销售先减少该原单未结应收，退货金额超过未结应收时才退款。当前入口只接受可重新销售商品，损坏品不得通过此入口入库。销售退货是现实商品退回，单据冲销是抵消错误业务事实，二者禁止混用。

Sales Reversal 已实现独立整单错单冲销。只允许尚未发生退货且赊账尚未收到任何核销付款的已过账销售单；商品按原成本回原仓，现结从原账户退回销售款，未收款赊账把应收标记为 `REVERSED`。原销售单改为 `REVERSED` 并保留原始历史，冲销记录保存原因、时间、操作者、明细、审计和 outbox。已退货或已收款单据禁止直接冲销；不得绕过限制直接改余额。

Customer Receipt Reversal 已实现整张客户收款反核销。原收款和核销关系不删除，独立反向单据恢复各笔客户欠款并从原收款账户减少相同总额；资金不足或相关销售已发生退货时必须拦截。完成反核销后，该收款不再阻止对应销售错单冲销。当前不支持部分反核销、客户真实退款或带下游退货的自动重算。

Supplier Payment Reversal 已实现整张供应商付款反核销。原付款和核销关系不删除，独立反向单据恢复各笔供应商欠款并向原付款账户加回相同总额；原付款标记为 `REVERSED`，反向单据、反向核销明细和资金流水均不可修改。当前不支持部分反核销；相关采购发生退货后必须阻止付款反核销。

Purchase Return 已实现关联原采购单的部分/整单退货。累计退货不超过原采购数量，库存不足时阻止过账；业务金额按原采购价先减少应付，已付款部分才记供应商退款到账，库存成本按退货时移动平均成本扣减。发生采购退货后，相关付款禁止直接反核销。

手机端主导航通过页面外层挂载固定在视口底部，常规页面必须始终可见并适配 `safe-area-inset-bottom`；不要把固定导航重新放进带变换动画的页面容器。打开销售开单窗口时，通过 `sales-dialog-open` 隐藏导航并锁定背景滚动，关闭后恢复。手机销售弹窗必须在视口中央保留安全边距，使用紧凑双列结算切换、压缩后的扫码区与双列表单。

销售开单的“散客现结 / 客户赊账”切换固定在弹窗顶部栏，不显示大段解释。选择客户赊账后，订单资料区允许直接快速新增客户姓名、联系电话、身份证号码、地址、按自然月计算的默认账期和可选客户人像；新增成功必须自动选中该客户且不得丢失当前销售商品。人像排在姓名前，可点击缩略图查看大图。身份证拍照只在客户端使用 Tesseract.js OCR，原图不上传或保存；身份证与地址可调用 Web Speech API 语音输入，地址可调用 Geolocation，未配置逆地理编码时只能回填坐标并要求人工补全。设备能力不可用时不得伪装成功。身份证号必须由服务端校验并加密保存，API 不得返回明文，只能返回末四位掩码；禁止把身份证或人像写入日志。客户人像仅用于资料留存，不得描述成人脸识别或身份比对。自然月账期使用 UTC 日历算法且月末取目标月最后一天，禁止用本地午夜转 `toISOString()` 导致日期提前一天。

库存采用 E 双层模式。默认“日常库存”服务店员，只展示真实数量、仓库、库存不足和搜索筛选；“专业账本”服务拥有 `inventory.post` 权限的老板/库管，保留期初、盘点、报损、成本、提交、过账与后续冲销审计。界面分层不能改变服务端正式账本不变量，也不能把未实现的调拨或冲销伪装成可用功能。

新增实物商品与第一笔库存采用“建档入库”快捷流程：同一表单填写商品、当前数量、单位成本、默认仓库和日期；数量大于零时 Inventory 在服务端事务内自动建立已过账单据、不可变流水和余额。该动作只允许商品在所选仓库没有历史流水时使用，不等同于系统上线期初库存，也不能代替后续采购入库。Catalog 仍不拥有可编辑库存数字。

销售弹窗不显示“销售开单”标题或其上方说明。表单视觉顺序固定为：结算方式、扫码或搜索商品、销售商品、收款账户与销售时间、提交操作。销售商品初始为空，扫码成功后立即新增商品行；重复扫描同一商品只增加该行数量，不能制造重复商品行。

销售弹窗不向操作员显示出库仓库，客户端自动选择启用中的默认仓库，服务端仍必须校验仓库并据此完成库存检查和成本过账。商品输入框同时支持名称、商品编号和条码检索。手机“拍照找货”当前只负责真实调起相机、预览照片和让操作员点选已有商品；照片不上传、不保存，自动图片识别尚未接入时必须明确提示，不能返回虚假识别结果。

门店销售的标准操作路径是“扫码或搜索加入商品 → 核对数量和价格 → 完成销售”。现结主按钮使用“完成销售并收款”，赊账使用“完成赊账销售”；这是客户端对创建、提交、过账三个正式接口的快捷编排，不是取消状态机或把过账移到客户端。快捷流程在创建后失败时必须保留并提示中间单据状态、阻止原窗口重复提交，并引导操作员从销售记录继续处理。
